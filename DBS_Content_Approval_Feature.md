# DBS Portal — Content & Approval Feature
**Digital Bloom Socials | Feature Specification**
*Version 1.0 — August 2026*

> Companion document to `DBS_Portal_Blueprint.md`. This spec describes **what the feature is and how it behaves**, not how to build it. Implementation sequencing, file structure, and migration order are to be determined against the live codebase.

---

## 1. Purpose

A monthly content review and approval workflow inside the existing portal.

Kelsey builds an entire month of content privately, then releases it to a client as a single event. The client reviews each post, approves it or requests changes, and the portal enforces revision limits, a deadline, and per-round billing.

Two problems this solves:

1. **Clients hovering mid-month.** Without a release gate, clients start requesting changes while Kelsey is still halfway through building the month.
2. **Unbounded revisions.** Feedback arriving in a trickle across many rounds is the failure mode. The software enforces batching and caps structurally rather than relying on contract language alone.

Secondary effect: this gives clients a weekly reason to log into the portal instead of only appearing twice a month to pay an invoice.

**Out of scope entirely:** the portal never posts to any social platform. Kelsey publishes to Instagram, TikTok, etc. manually. This feature manages approval only.

---

## 2. Core Concepts

| Term | Meaning |
|---|---|
| **Cycle** | One client, one month. The unit that gets released, deadlined, and locked. |
| **Item** | One scheduled post. Has a date, platform, format, caption, and one or more assets. |
| **Asset** | One video or image belonging to an item. Carousels have several. |
| **Release** | Kelsey's action that makes a cycle visible to the client. Per-client, per-cycle. |
| **Round** | One batch of revision requests on one item. Round 1 is included; round 2+ is billable. |
| **Lock** | Cycle state where the client can no longer act. Triggered by deadline or by Kelsey. |

## 3. Technical Design

### 3.1 Storage split

Three systems, each holding what it's suited for.

| Data | System | Why |
|---|---|---|
| All metadata and state | Supabase Postgres | Source of truth. Row volume is negligible. |
| Photos | Supabase Storage | Already built and in use. |
| Review videos | Cloudflare Stream | Transcoding, adaptive bitrate, poster frames. |
| Final client deliverables | Supabase Storage | Unchanged — existing files feature. |
| Marketing site media | Cloudinary | Unchanged — separate concern. |

**Postgres is the source of truth.** Cloudflare Stream holds bytes only. The Stream video ID is stored on the asset row. There is no foreign key relationship protecting that link, which has consequences documented in §3.5.

### 3.2 Why Cloudflare Stream

Supabase Storage is a plain file store — no transcoding, no adaptive bitrate, no poster frames. A client on a weak connection would download the full original before the first frame, seeking would be unreliable, and the calendar grid would have no thumbnails.

Stream generates a quality ladder automatically on upload. Kelsey uploads a 4K file; the client's device receives an appropriate rendition for its connection. **No downscaling is required on Kelsey's side and none should be built.**

Stream pricing:

- Storage: $5 per 1,000 minutes stored per month, prepaid, billed on **duration, not file size**
- Delivery: $1 per 1,000 minutes delivered, post-paid
- Ingress and encoding: free
- Renditions generated by Stream do **not** consume storage
- No separate egress or bandwidth fees

### 3.3 Cost model

Assumptions: 5 clients, ~20 posts per client per month, ~60 videos per month, average clip length 6–15 seconds (10s used below), ~40 photos per month, each post viewed ~6 times across review and revision.

**Cloudflare Stream:**

| Line | Math | Result |
|---|---|---|
| New video per month | 60 × 10s | 10 min |
| Stored after 12 months | 10 × 12 | 120 min |
| Stored after 60 months | 10 × 60 | 600 min |
| Storage cost | one 1,000-min block covers 5+ years | **$5/mo** |
| Delivered per month | 60 × 0.167 min × 6 views | 60 min → **$0.06** |

The second $5 storage block is not reached until roughly 6,000 stored clips — approximately year eight at this volume. **No retention or auto-deletion job is required.**

**Supabase, against free-tier limits:**

| Line | Math | Free limit |
|---|---|---|
| Photo storage, year 1 | 40 × 1 MB × 12 = 480 MB | 1 GB file storage |
| Egress per month | photos + JSON ≈ 300 MB | 5 GB storage egress |
| Database rows per year | ~1,200 items + assets ≈ 5 MB | 500 MB database |

**Total added cost: ~$5/month.**

### 3.4 Supabase Pro

Production is upgrading to Supabase Pro at $25/month. **This is not driven by this feature's storage needs** — photos would fit the free tier for over a year.

The driver is that the free plan has no backups and no SLA. Production holds live client records, invoices, income, expenses, and mileage data with no restore point. Pro adds daily backups.

### 3.5 Cloudflare Stream integration requirements

Four items that must be handled correctly.

**a. Signed URLs — access control**

Stream video URLs are public by default to anyone holding the URL. Clients must not be able to access another client's content.

Required: `requireSignedURLs` enabled on every video, plus a signing key. The server mints a short-lived playback token per request after verifying the requesting client owns that content item. Same pattern as the existing Supabase signed-URL implementation.

**b. Transcoding is asynchronous**

Upload completion and playability are separate events. An uploaded video is not immediately watchable.

Required: poll Stream's `readyToStream` flag. The asset row carries a processing state until the flag flips, then moves to ready. Kelsey's **Release** action must be blocked until every asset in the cycle is ready — otherwise clients open dead players.

At 6–15 second clip lengths this resolves within seconds and should be largely invisible to Kelsey.

**c. Explicit deletion on replace**

When Kelsey accepts a revision, the replacement video is a new Stream upload and the superseded video must be explicitly deleted from Stream. The same applies to any content item or asset row deletion.

Nothing in the database protects against this. An orphaned Stream video leaks storage silently with no error surfaced anywhere.

**d. Upload duration cap**

Direct Creator Upload tokens reserve their `maxDurationSeconds` against the storage block until the upload completes or the link expires. This must be set tightly (~120 seconds) so a stalled or abandoned upload cannot reserve a large portion of the block.

### 3.6 Upload path

Vercel's serverless body limit (~4.5 MB) makes proxying video through an API route impossible.

Required pattern: the server mints a one-time Direct Creator Upload URL; the browser uploads straight to Cloudflare Stream. Structurally identical to a Supabase signed upload URL.

TUS resumable upload is native to this path. A dropped connection resumes mid-file rather than restarting.

### 3.7 Background upload behavior and its limits

Uploads run in the background while Kelsey continues working elsewhere in the portal. She uploads a clip for one date and moves to the next without waiting.

**Platform constraint — this must be understood before designing around it:**

| Scenario | Behavior |
|---|---|
| Navigating between pages inside the portal | Upload continues |
| Hard refresh | Upload stalls, resumes on return |
| Closing the tab | Upload stalls, resumes on return |
| iPhone/Safari — phone locks or app backgrounds | iOS suspends JavaScript; upload stalls, resumes on return |
| Chrome on desktop | More tolerant of backgrounding |

There is no background-upload API in Safari. "Close it and walk away" cannot be built for iPhone. Nothing is lost in any of these cases — TUS resumes from the interruption point — but the upload does not complete unattended.

**Operational guidance:** Kelsey should do bulk month-building on desktop Chrome. Phone uploads work but require the tab to stay open.

Upload failures must surface a clear, retryable notification rather than failing silently.

### 3.8 Reference schema

Established design. Five tables, all additive. Nothing modifies existing tables except an optional foreign key from `revision_rounds.invoice_id`.

```sql
content_cycles              -- one row per client per month
  id, client_id
  month date                -- first of month
  revision_deadline timestamptz
  included_rounds int default 1
  extra_round_price numeric
  status: drafting | in_review | locked

content_items
  id, client_id, cycle_id
  scheduled_for timestamptz
  platform: instagram|tiktok|facebook|youtube|pinterest
  format:   reel|feed|story|carousel
  caption text
  status: draft|in_review|changes_requested|approved|published
  current_round int default 1
  approved_at, approved_by, sort_order

content_assets              -- separate table: carousels are multi-asset
  id, content_item_id, position int
  kind: video|image
  provider: 'stream'|'supabase'
  external_id text          -- Stream UID or storage path
  duration_seconds, width, height, bytes
  replaced_at               -- soft version history across revisions

revision_rounds             -- the atomic unit
  id, content_item_id, round_number int
  is_billable bool, price numeric
  submitted_at, submitted_by     -- NULL until client submits
  status: open|addressed, resolved_at
  invoice_id                -- set when billed

revision_notes              -- children of a round
  id, round_id
  category: clips|caption|music|pacing|text_overlay|cover|schedule|other
  timestamp_seconds numeric  -- nullable; for scrubber comments
  body text
```

### 3.9 Other technical notes

- **Media is 9:16 vertical throughout.** Never cropped to square or 16:9.
- **`scheduled_for` timezone** — use the `new Date(y, m-1, d)` constructor path. This trap has already been hit once in this codebase.
- **Do not build a second calendar.** Extract the existing month grid into a presentational component that accepts an events array, then feed it shoots and content items with a filter toggle.
- **Deadline enforcement runs as a daily scheduled job.** Any cycle past `revision_deadline` still in `in_review`: all non-approved items flip to approved with `approved_by = 'auto'`, cycle status → `locked`.
- **Stream is not an archive.** Stream re-encodes and does not reliably return a pristine original. Kelsey's 4K masters stay on her own drive; final client deliverables stay in Supabase Storage via the existing files feature.

## 4. Kelsey's Workflow

### 4.1 Building the month

Kelsey works in a content calendar view. She can see all clients, or filter to a single client.

For each post she sets the date, uploads the video or image, and enters the platform, format, and caption. Upload proceeds in the background; she moves to the next date without waiting.

**Nothing she uploads is visible to the client.** There is no per-post send action. Individual posts do not have their own release state.

### 4.2 Release

Release is a single action, per client, per cycle.

When Kelsey clicks **Release** for a client:

- The entire month becomes visible to that client at once
- The client receives an email notifying them content is ready for review, with a link into the portal
- The cycle enters review state

Release is blocked until every asset in the cycle has finished transcoding.

This gate exists specifically so clients cannot begin requesting changes while Kelsey is midway through the month.

### 4.3 Deadline

Kelsey sets the revision deadline per cycle. It is a stored timestamp, not a countdown from release.

**Only Kelsey can extend it.** There is no self-serve extension on the client side — a client-granted extension would be used routinely and would effectively become the default deadline.

Extending is a single field change. It does not require re-release, does not reset the cycle, and does not affect any client progress: submitted items stay submitted, in-progress notes stay in place.

At the deadline the cycle locks automatically and all untouched items auto-approve.

### 4.4 Adding a post after release

If Kelsey forgets a post and needs to add one after releasing:

1. Unrelease the cycle
2. Add the post
3. Re-release

Because the deadline is a stored timestamp rather than a countdown, client progress survives this. Submitted items remain submitted. The client sees one new item appear.

### 4.5 Monitoring progress

Kelsey sees a rollup of where the client stands — approved, revised, and untouched counts.

This is informational. It tells her whether to reach out or whether a client has likely finished, but she is not required to act on it.

### 4.6 Manual lock

Kelsey has a **Lock now** button for cases where a client confirms they are finished before the deadline.

The automatic deadline lock is the primary mechanism. She cannot reliably distinguish "finished" from "paused partway through" by watching the rollup, so locking is not her responsibility by default.

### 4.7 Reviewing revision requests

As each item is submitted by the client, it appears for Kelsey immediately. She sees requests arrive in real time even while the client continues working through the queue.

Seeing a request does not mean she must act on it yet.

For each item she can **accept** or **deny** the revision request.

**Accept:**
- She uploads the new version
- She can play the current and new versions side by side before committing
- Accepting replaces the old version with the new one and resolves the request
- The superseded Stream video is deleted

**Deny:**
- Requires a written reason
- Requires confirmation before committing
- The client sees the reason

### 4.8 Working state and re-release

While Kelsey is addressing revisions, the client is locked out of further action. The client sees an informative state indicating she is working on their changes.

When she is done, she re-releases the cycle. This opens the next round of revisions.

Round 1 is included. Round 2 and beyond are billable.

### 4.9 Billing visibility

Kelsey sees accrued revision charges per client as they occur. See §6.

## 5. Client Workflow

**Design constraint:** some clients are older and less technically confident. Simplicity governs every decision on this side.

### 5.1 Notification

The client receives an email when Kelsey releases the cycle, containing a link into the portal.

### 5.2 Review queue

All posts in the cycle enter a review queue. The client moves through them one at a time.

**The queue is resumable.** They can review a few posts, leave entirely, and return later to exactly where they left off. Progress is never lost.

### 5.3 Reviewing one post

For each post the client can:

- **Approve** it
- **Request changes**

Requesting changes uses a guided form rather than an open text box:

- **Preset categories** — clips, caption, music, pacing, text overlay, cover, schedule, other
- **A comment field per selected category**
- **Timestamp notes** — the client can leave a note at a specific point in the video, anchored to that timecode

Guided categories exist because free-text feedback produces unactionable notes. Categories produce specific, addressable ones.

### 5.4 Per-item submission

The client submits **each item individually** as they finish it. There is no global submit button at the end of the queue.

**A submitted item is locked.** The client cannot reopen it to add more feedback. They can continue working through the rest of the queue, but an item they have sent is closed.

This is the mechanism that makes the whole design work. Without it, feedback dribbles in indefinitely and the round structure is meaningless.

### 5.5 Completing the queue

When the client finishes the queue, they take no further action. The portal informs them that Kelsey will review their requested changes.

### 5.6 Locked state

Once the cycle locks — by deadline or by Kelsey — the client sees an informative state indicating Kelsey is working on their revisions. No further edits are possible.

### 5.7 Deadline

The deadline is set by Kelsey per cycle. Clients cannot extend it themselves; they contact Kelsey, who extends it if she chooses.

At the deadline, any item the client never touched is automatically approved. Silence becomes approval.

### 5.8 Subsequent rounds

After Kelsey re-releases, the client can request changes again. From round 2 onward this carries a charge.

**The price must be shown before submission,** in a confirmation step naming the round number and the amount added to their next invoice. This is captured consent and is what prevents billing disputes.

**Tone requirement:** the framing must not feel punitive. This is a stated design goal; specific wording is undecided.

## 6. Billing

### 6.1 Rounds

| Round | Billable |
|---|---|
| 1 | No — included |
| 2+ | Yes — `extra_round_price` |

A round in which **every** item was denied by Kelsey is not billed.

### 6.2 Accrual model

Charges **accrue as unbilled line items** flagged to the client. They do not create invoice drafts and they do not post as income on submission.

Reasoning: multiple drafts per month would require Kelsey to remember to merge them into the real monthly invoice, creating a double-billing risk.

Flow:

1. Client submits a billable round → an unbilled charge is recorded against that client
2. Kelsey sees the accrued charge immediately, as pending — not as income
3. When she builds that month's invoice, unbilled charges appear as one-click additions
4. Adding a charge stamps it as billed (`revision_rounds.invoice_id`)
5. **Income posts when the invoice is paid**, through the existing invoice and payment flow

### 6.3 Why income posts on payment

The business is cash-basis. A charge is income when the money is in hand, not when the client submits a request. Posting on submission would overstate revenue and inflate the tax set-aside.

## 7. Platform Support

The feature must work fully on desktop and on iPhone, matching the rest of the portal.

Kelsey is phone-first for most of her portal use. The exception is bulk month-building, where desktop Chrome is recommended due to the upload constraint in §3.7.

## 8. Decisions Log

| Decision | Choice |
|---|---|
| Video storage | Cloudflare Stream |
| Photo storage | Supabase Storage (unchanged) |
| Source of truth | Supabase Postgres |
| Supabase plan | Pro — $25/mo, for daily backups |
| Client-side downscaling | Not built — Stream transcodes server-side |
| Retention / auto-delete job | Not built — storage never becomes a cost factor |
| Release granularity | Per client, per cycle. No per-post send. |
| Post added after release | Unrelease → add → re-release. Progress preserved. |
| Deadline owner | Kelsey, custom per cycle |
| Deadline extension | Kelsey only. No client self-serve extension. |
| Deadline expiry | Auto-lock, untouched items auto-approve |
| Manual lock | Available to Kelsey as an override |
| Client submission | Per item, immediately visible to Kelsey |
| Submitted item | Locked. Cannot be reopened by client. |
| Queue resumability | Yes — exit and return without losing progress |
| Revision feedback format | Preset categories + per-category comment + timestamp notes |
| Round 1 | Included |
| Round 2+ | Billable, price shown before submission |
| Deny | Requires written reason and confirmation. Client sees reason. |
| Fully-denied round | Not billed |
| Billing mechanism | Unbilled line item accrual, not invoice draft |
| Income recognition | On invoice payment (cash basis) |
| Social publishing | Never. Kelsey posts manually. |
